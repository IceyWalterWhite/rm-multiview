## 1. 它是什么

从页面上**已经在播的十路 FPV 画面**里，用计算机视觉反解出每台机器人的位置、朝向、血量，
画到一张 3D 场地沙盘上。**零额外带宽**——`drawImage(video)` 读的是解码器已经产出的那一帧。

官方在每一路第一视角里都渲染了同一套 HUD：右下小地图上的绿色圆盘就是「我」，
左下血条上写着「当前/上限」。**十路各看各的自机**，所以天生没有多目标跟踪里
最难的数据关联问题——每台机器人只由它自己那一路负责。

## 2. 数据流

```
<video>×10                    ← 页面上已经在播的画面
  │  sampler.ts               整帧 drawImage 一次 + 四次 getImageData
  ▼
Frame（全尺寸，只有 ROI 填了真像素）
  │  streamPhase.ts           逐路自判 live / dead / off
  │  marker.ts  hp.ts         小地图绿盘 → 位置+朝向；血条白字 → 当前/上限
  │  objectives.ts            顶部记分板 → 双方基地/前哨站血量
  ▼
tracker.ts（每路一个）        区分「没看见」与「死了」，上限跳变要连续确认
  ▼
fleet.ts                      十路汇聚 + fieldMap 换算 + 目标血量融合
  ▼
SandboxSnapshot               { robots[], objectives, withHud, live, located }
  │  useSandbox.ts            React 接线：什么时候跑、video 在哪
  ▼
render/scene.ts               three.js + field GLB，弹簧插值、贴地法向
```

`src/sandbox/` 下除 `sampler.ts` 与 `render/` 外**全是纯函数**，不碰浏览器 API。
所以同一套代码既能在浏览器跑（方案 A，现在这样），也能搬到服务端跑（方案 B）。

## 5. 标定常数与各自的置信度

全在 `src/sandbox/fieldMap.ts`，每条都带推导。按可信度从高到低：

**① 横轴（钉死，误差 ~2cm）**
两侧基地图标 u=0.0595/0.9395，中点 **u=0.4996** ↔ 场地 X=0；
由 `field_final.glb` 离线解出基地/飞镖站灯条在 **x=±12.745 m**，
按「小地图横向满幅=木质底板 29.01 m」反推应落在 0.0603/0.9389。
旁证：增益点六边形落在 ±7.5 与 CAD 一致；**开局出生区分布独立复现**。

**② 朝向**
`yaw = heading + π`。两个轴都翻向，方向向量取负两次 = 整体旋转 π，**不是取负**。
最容易凭直觉写错的一处，`fieldMap.test.ts` 里逐象限钉着。

**③ 红蓝不镜像**
两队看到的是**同一张小地图**（取双方英雄同时刻对比确认）。
「按阵营翻转」这一类坑整个不存在。

**④ 纵轴（明显弱于横轴）**
中心 v=0.47215 ↔ Y=1.6245 可靠；尺度取**均匀缩放** 16.32 m。
方向由数据判定（含负值扫描：+16.0 落面率 67.9% vs −17.0 的 60.7%），
但**优势只有 7 个百分点，目标函数在 13~17 m 之间相当平**。
→ 复核需要一个**偏离中线的地标**。用过的地标（基地、增益点）全压在 y≈1.62 中线上，
对纵向零约束力。前哨站是天然候选（CAD 红方 (3.09,6.41) / 蓝方 (−3.05,−1.32)），
但**靠肉眼在小地图上指认的结果自相矛盾，未采信**。接手请从「稳定检出前哨站」入手，
不要沿用目测。

**⑤ 空中那组（最弱）**
`DRONE_MINIMAP_U0/V0/SPAN_X/SPAN_Y`。空中画的是同一张地图但裁切不同。
推导链：基地图标跨距比（地面 0.9017 / 空中 0.8562）→ 像素尺度比 0.6362 →
均匀缩放 → 纵向。**串了三层推断且没有任何地面真值可对。**

## 6. 会绊倒你的坑

**① 十路读数不是十个独立样本**
战略目标血量长在十路共享的同一条记分板上。它们是同一块像素的十份转码副本——
源头数字一糊，**十路会同时朝同一个方向读错，而且连续好几拍**（实测连续 3 拍八路全错）。
跨路多数票几乎不提供保护，「连续确认 N 拍」也不提供。叠上单调约束更糟：
锁到偏低的误读后本回合再也回不来。
→ `objectiveFusion.ts` 改成**按时间衰减累积 conf² 证据**（真正独立的轴是时间）。
改前 redBase 判成 3936、blueBase 判成 4965，两个都错；改后 3946 / 5000，两个都对。
**任何「多路看同一个源」的融合都适用这条。判断独立性看噪声来源，不是观测者数量。**

**② 判「HUD 在不在」要看暗像素，不是亮像素**
赛事 HUD 无论是否灰化，元素之间永远留深色底，记分板区域亮像素占比落在 0.658~0.948；
导播切过去的转播镜头/宣传卡是整张照片，几乎每个像素都过门槛，**恰好 1.000**。
门限 `HUD_ABSENT_LIT = 0.97`。**等待卡的 lit 也是 1.000**——旧的全局开赛标志
当初存在就是为了防它，这条判据直接把它认掉了。

**③ 阵亡有两种像素形态**
①整体灰化（sat=0.000，小地图变黑白、血条被「收起该面板」顶掉，`readHp` 失败）；
②**彩色 HUD + 血量归零**（`0 / 300`，血条空了所以血条阵营色也是 0）。
只用「血条上还有没有阵营色」判开播，会把②误判成「没开播」——
而那正是小地图完全可读的时刻。

**④ 空中机器人没有血量**
那一路没有血条也没有记分板，三个 ROI 落在 FPV 画面本身（记分板区域实测整片全黑）。
对它调 `readHp` / `readObjectives` 不是「读不准」，是**问了一个不存在的问题**。
已在 `streamPhase.observePhase` 从源头拦掉。无人机也不会阵亡。

**⑤ catalog 对象身份 ≠ 名单变了**
`useCatalog` 在 HLS 签名过期时重取，产出**内容相同的新 catalog 对象**。
按对象身份重建采样链，会把十路的最后位置与融合证据全部清零，
而签名过期在一场比赛里会反复发生。→ 用 `fleet.rosterKey(members)` 判断，
`fleet.test.ts` 有回归测试。

**⑥ 隐藏标签页拿不到一帧**
Chrome 在 `document.hidden` 的标签页里根本不启动媒体加载，MediaSource 永不 open。
**测视频只能用 Playwright**（它的页面恒为 visible），claude-in-chrome 做不了。

**⑦ 离线像素是 BT.601，浏览器是 BT.709**
色相差约 3。拿离线抽帧标定 HSV 阈值会系统性偏（这个坑真实发生过：
`SELF_MARKER_GREEN` 上沿 86→90，位置检出 72.5%→81.2%）。
`cv2.VideoCapture` **忽略**容器的色彩标签，加 `bt709` 标签没用。
→ `tools/sandbox/README.md` 有详述。**离线的绝对检出率不可外推到浏览器**，
只有同数据集的参数差值可信。

**⑧ `tsconfig.app.json` 不含测试文件**
改完测试必须另跑 `npx tsc -p tsconfig.test.json`，否则类型错会漏（vitest 不做类型检查）。

**⑨ 分母必须条件化**
「HUD 亮着的地面帧」才是位置检出率的分母。不条件化的话，回合间歇的宣传卡
会把分母冲垮，得出的数字毫无意义。这是本模块最重要的评估纪律。

## 7. 怎么复现验收

```bash
# 1. 起本地服务（直接连现网 CDN，不需要代理）
npm run dev -- --port 5199 --host 127.0.0.1

# 2. 用 Playwright 打开（不能用普通浏览器后台标签页，见坑⑥）
#    滚到 #sandbox，等 GLB 加载完

# 3. 开发构建下 window.__rmSandbox 挂着最新快照（生产构建会被 DCE 掉）
window.__rmSandbox.located          // 有位置可画的路数
window.__rmSandbox.live             // 正在放比赛且活着的路数
window.__rmSandbox.withHud          // HUD 在的路数；间歇时整体掉 0 是正确行为
window.__rmSandbox.robots           // 逐台的 pose / hp / status / phase
```

**离线评估集**（像素不入库，在 `D:/rmcap/`，没有时相关测试整组跳过）：

```bash
npx vitest run src/sandbox/streamPhase.eval.test.ts   # 逐路自判
npx vitest run src/sandbox/fleet.eval.test.ts         # 端到端汇聚
npx vitest run src/sandbox/fieldMap.eval.test.ts      # 坐标变换
npx vitest run src/sandbox/browser.eval.test.ts       # 浏览器 vs 离线像素对照
```

抓新数据集的脚本在 `tools/sandbox/`。

## 9. 下一步

按价值排：

1. **稳定检出前哨站** → 复核纵轴尺度，顺带给空中那组常数一个真正的约束。
   这是目前最大的精度瓶颈。
2. **红方空中路在 540p 下检不出**（自机只剩 9 个像素落进色相窗，蓝方 1092）。
   是分辨率下限不是算法问题——1080p 下同一检测器 86.9%。
   要么给空中路单独提清晰度，要么接受它。
3. **音频主判据接进来**（`worktree-timecode-sync` 的 `teeLoader.ts` / `tsDemux.ts`）。
   现在不接也能工作，但它是无抖动的二值信号，比视觉判据强。
   注意：音频取自**下载时刻**，比播放画面早一个缓冲深度（实测 10s），按画面消费会早判。
4. **卡尔曼平滑**。目前靠渲染层的临界阻尼弹簧 + 陈旧度褪色，上线后若抖动明显再补。
5. **哨兵血量**。哨兵没有操作手视角拿不到位置，但顶部记分板上有双方全体机器人的血量条——
   那是十路共享的同一份全局信息。尚未实现。
