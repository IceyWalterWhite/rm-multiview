# 时码同步

> 让 11 路视角播同一瞬间的画面。
> 状态：功能可用，已合入 main（本地，未 push）。**侧路卡顿已定案**（第 6 节），修法待实施。

---

## 1. 要解决什么

11 路流各自独立传输，同一时刻打开，画面内容并不在同一时刻——实测能差到 20 秒以上。观众看主视角刚打起来，侧路还停在开赛前。

## 2. 原理

每个分片的文件名里带一个时间戳（`{unix秒}_{序号}.ts`），那是**切片服务器写盘的时刻**。但画面是更早拍的，中间隔着编码、回传、转码。就像照片的"上传时间"不等于"拍摄时间"。

```
画面时刻 = 文件名时间 − 偏移量
```

**偏移量**就是这一路从"拍下来"到"传上来"耽误了多久。算出每一路的画面时刻，就能对齐：谁慢了加速追，谁快了等一等。

### 偏移量怎么测

比赛时**所有视角都放着同一份解说声**。把侧路的声音和主视角的声音做互相关，错开多少秒一目了然——那就是这一路的偏移量。

每组实测值按「主视角 ID + 主分辨率 + 侧视角 ID + 侧分辨率」保存，当天有效，存在 `localStorage['rm.sync.offset.v3']`。

> **不要再把它拆成"档位常量 + 每路残差"**。早期版本这么做过：存的时候减去档位常量、用的时候再加回来，净效果为零，反而让存档绑死在常量上（常量一改旧存档全部失准）。测出多少存多少即可。

### 没声音的时候

对齐**不需要声音**，声音只用来测偏移量。对齐靠的是文件名时间戳，垫片阶段照样在传分片。赛间就直接用当天已测好的值。

赛间也必须保持对齐，否则开赛那一刻各路是错开的，要花一分多钟才追平。

### 某一路没声音是正常的

那台机器人可能没上场，画面是空位、音频不是场上混音，自然对不上。本轮测不出时，只复用四项元数据完全匹配的旧实测值；没有旧值就保持该路不同步，绝不使用先验猜测。

## 3. 代码地图

```
src/sync/
  nameClock.ts   解析文件名时间戳，估计 E = median(文件名秒 − 分片起始位置)
  xcorr.ts       FFT 互相关（无依赖）
  tsDemux.ts     从 MPEG-TS 里抠出 AAC 音频和 PTS
  audioCalib.ts  测偏移量 + 开赛探针
  controller.ts  纯决策函数，所有阈值集中在此
  engine.ts      1Hz 控制回路，主视角为基准
  teeLoader.ts   包一层 hls.js 的 fLoader，把正在下载的分片字节抄一份（零额外带宽）

src/components/
  SyncControl.tsx  主视角右上角的控件（开关 + 微调面板）
  SyncBadge.tsx    机位角标
```

**数据通路**：hls.js 下载分片 → `teeLoader` 抄一份 → `tsDemux` 抠音频 → `OfflineAudioContext` 解码 → 能量包络 → 互相关 → 偏移量 → `engine`。

播放和测量是两条**物理隔离**的路：`OfflineAudioContext` 从不连接扬声器，侧路 `muted` 属性也从不被碰。侧路静音是设计前提——正因为静音，±4% 变速才听不出来。

### 控制策略（controller.ts）

主视角是基准，**永不调整**。侧路按误差分档：

| 误差 | 动作 |
|---|---|
| < 0.15s | 不动（0.05~0.15 是滞回带，防边界振荡） |
| 0.15 ~ 2s | `playbackRate` ±4% |
| > 2s，存粮充足 | seek，且**落点后必须留 4 秒存粮** |
| > 2s，存粮不足 | 退回变速慢慢追 |
| 存粮见底(<2s) | 贴边等待 |

### 关键判断

- **带宽不是瓶颈**：需求 19.9 Mbps，实测吞吐 19.5~21.5 Mbps、占空比 3~8%，其余时间在等分片产出
- **偏移量每天不同**，甚至一天内也可能变（推流重启会改变它）
- **禁止使用档位先验**：偏移量会随分辨率、视角和推流任务变化。没有元数据完全匹配的实测值时，该路不参与同步。

## 5. 踩过的坑

**互相关必须用整流能量包络，不能用原始 PCM。** 主视角是导播混音、侧路是场馆通道，同一节目的不同混音在波形级几乎不相关（过不了峰值门限），能量包络则强相关。

**跨视角的画面不能做互相关。** 各路 FPV 内容本就不同，相关曲线是平的（实测 sharpness 1.0~1.2，无峰）。垫片画面同样不行——变化太慢。

**画面平均亮度不能用来判断切换。** 阈值 0.33 落在比赛画面实际亮度 0.30~0.37 区间内，单路能产生 79 次误报。要判画面用血条阵营色。

**累计计数器做性能对比必须取差分。** `droppedVideoFrames` 是累计值，含起播阶段的大量掉帧；直接用会得出 4~15% 的掉帧率，取 30 秒增量后实际只有 0.1%——差两个数量级，结论完全相反。

**`useSyncExternalStore` 的 getSnapshot 必须引用稳定。** 每次返回新对象会直接无限重渲染。这就是 `engine.statusCache` 存在的理由。

**关闭同步时必须清空状态缓存。** `tick()` 在关闭后直接 return，缓存会冻结在最后一帧，角标永远定格在关闭那一刻的读数（08-05 实测 30 秒纹丝不动）。

**seek 落点必须留够存粮。** 早期 `EDGE_MARGIN = 0.5`，误差大时会跳到缓冲末端只剩 0.5 秒，播完断粮 → 卡住 → 等下一片的 5 秒里误差又涨 → 再跳 → **死循环**。现在改为落点后留 4 秒。

**hls.js 把起播位置 clamp 到 `edge − playlist 总长`（`dist/hls.js:33761`：`min = edge − totalduration`）。** 按秒配的 `liveSyncDuration` 在 playlist 短的高码率路上会被**静默截断**。两路 playlist 长度不同时，光配置就能造出非对称落后量——本站主视角 6s、侧路 15s，`liveSyncDuration: 12` 一边被砍到 6、一边完整生效（第 6 节）。

**Chrome 150 起桌面版 `canPlayType('application/vnd.apple.mpegurl')` 返回 `'maybe'`。** "原生优先"的分支会让 hls.js 在现代 Chrome 上整体旁路。现在是 MSE 可用一律走 hls.js。

**测量前先确认环境。** 官方收播过程中的数据（缓冲见底、卡顿频次）不能当常态用。

## 6. 已定案：侧路卡顿 = 配置层非对称 + 同步推近边缘

侧路（10 路 540p）持续卡顿 **64.5 次/分**，主视角 **0 次**。

**根因链条**：

1. `HLS_CONFIG.liveSyncDuration: 12` 对主视角被 hls.js 截断成 **6**（`dist/hls.js:33761`，`min = edge − totalduration`）。主视角 playlist 只有 3 片×2s = 6s；侧路 3 片×5s = 15s，12 完整生效。**配置层就非对称 6 秒**。
2. 同步再按 offset（~4.5s）把侧路推近直播边缘 → 存货只剩 **2.3 秒**，而侧路分片是 5 秒一个。
3. 误差 −8.65s 本该 seek，但存货 < `SEEK_LANDING_BUFFER`(4) → 永久退回变速档。
4. 1.04 倍速每 5 秒周期净亏 0.2 秒 → 触底断粮卡顿 → 卡顿期间误差反增 → 继续加速。**病态极限环**。

| 08-06 现网三组对照 | 卡顿 | 误差 |
|---|---|---|
| A 现状 | 64.5 次/分 | 永不收敛 |
| B 关同步 | 11.4 次/分 | — |
| C 主视角基准后移 4.5s | **9.3 次/分** | **0 ~ 0.1s** |

**解法**：主视角首次起播前**多等 6 秒**，落后量从 ~7.5s 拉到 ~13.5s——等价于让 `liveSyncDuration: 12` 对它真正生效。侧路目标随之变成 13.5 − 4.5 ≈ 9 秒 > 5 秒分片周期，存货就安全。`engine.ts` / `controller.ts` 一行不改。

**侧路绝不能跟着延迟**：侧路本就起播在 edge−12，再延迟变 edge−18，同步要往前推 9 秒，而 `maxBufferLength: 8` 让它跳不回来。

**延迟起播安全（08-06 实测）**：主视角暂停 6 秒期间 `currentTime` 漂移 0.0000（60 次采样）、hls.js 位置调整 warn 0 条、`readyState` 全程 4，lag 8.53 → 14.43，恢复播放后稳定 14.35 达 30 秒。没被 `synchronizeToLiveEdge` 拉回：暂停时 buffer 满、`readyState` 恒为 4，其触发条件 `!withinSlidingWindow && readyState < 4` 从未成立。

**已排除**：
- 不是带宽——08-06 实测吞吐 19.5~21.5 Mbps、占空比 3~8%、平均并发 0.77，129.5 秒窗口内每路都拿满 26×5s = 130 秒内容
- 不是主线程阻塞——长任务 0 个，校准冷跑 182ms / 热跑 1ms，开赛探针 50ms
- 不是 seek 死循环——修复后 seek 从每路数次降到 0，但卡顿依旧

### 现网装探针（08-06 踩过）

- 装探针前**等 25 秒**让 11 路起播完，否则采到的全是起播态
- 装好后只用 `browser_evaluate`——**写文件会触发 Vite reload**，探针直接没
- 开头先 `performance.setResourceTimingBufferSize(20000)` + `clearResourceTimings()`：默认只存 250 条，满了**静默停记**
- 存货口径取**包含 `currentTime` 的那个连续块**，不能用 `buffered.end(length − 1)`
