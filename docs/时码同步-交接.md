## 2. 用户已经确认的同步规则

同步**禁止使用任何 tier prior / 分辨率先验**。

每一路只有在以下四项 metadata 完全匹配时，才允许使用 offset：

```text
主视角 ID + 主视角分辨率 + 侧视角 ID + 侧视角分辨率
```

行为规则：

1. 有完全匹配的实测 offset：参与同步。
2. 没有完全匹配的实测 offset：保持原速，不 seek，不变速，状态为 `off`。
3. 本轮重新校准测出新值：只替换对应 metadata profile。
4. 本轮没有测出某一路：保留旧的、metadata 完全匹配的实测值。
5. 切换到没有 profile 的主/侧分辨率组合：该路暂不同步。
6. 切回已有 profile 的组合：恢复使用旧实测值。
7. 旧 `v2` 存档没有侧路分辨率字段，不能安全迁移，必须忽略。

## 3. 本轮已经完成的代码改动

### 3.4 互相关修复

`src/sync/xcorr.ts` 已改为 lag-specific、overlap-aware Pearson NCC：

- FFT 只计算 `Σab`

## 7. 已实测、尚未处理的风险

> 2026-08-08 已用生产模块探针、MockHls 受控夹具和真实预览逐项完成验证。下面的“已复现”是可稳定触发的现状，**不是**仍待确认的猜测；本次没有修改生产代码。

| 优先级 | 风险 | 实测证据与根因 |
|---|---|---|
| P1 | 主视角在主音频解码期间换分辨率，旧 buffer 会写入新主参照 profile | 已复现：探针测得 `count=1`，最终 `mainRef=main|720p`，但校准样本来自旧 `1080p` 主路。`calibrate()` 在 `await assemble(mainBuf)` 后才取 `mainRef`（`src/sync/audioCalib.ts`）。 |
| P1 | 退役主视角的 buffer 仍会被当作主基准 | 已复现：把旧 ID 降为 side、注册新 main 后，旧缓冲的 `isMain:true` 仍被 `calibrate()` 首先选中，探针 `count=1`。 |
| P2 | `stop()` 后，已启动的校准完成仍可写 profile | 已复现：启动校准、调用 `stop()`、放开挂起 decode 后，探针仍测得 `count=1`。`stop()` 只清计时器，不取消在途 Promise。 |
| P2 | 一秒匹配音频也能入库 | 已复现：`assemble()` 仅拒绝小于一秒的窗；一秒输入校准成功 `count=1`。 |
| P2 | 手动与定时校准并发时，手动调用会误报“无可用音频” | 已复现：`manualResult=0`、`periodicResult=1`，且最终 offset 已写入；第二个调用因 `calibrating` 锁直接返回 0。 |
| P2 | 关闭同步仍会执行主视角 startup hold | 已复现：真实预览的 `pause()` 注入探针捕到同步关闭时 `main-video` 在 `currentTime=0` 被暂停。`holding = sync?.isMain === true` 不读取同步开关，且 `MainStage` 始终传 binding。 |
| P2 | 同一 `src` 下 sync binding 变更不会重建 HLS | 已复现：受控重渲染改为新 `engine/id/tier` 后仍只有一个 HLS 实例，旧 engine 收到 `onFrag('old')`，新 engine 从未 register。effect 依赖仅含 `videoRef/src/keepAliveWhenHidden`，`syncRef` 只更新 ref。现网仅签名变更通常会改 src，但 URL 稳定的源更新或组件改造会触发。 |
| P2 | hold 的 6 秒内开启声音，放行 `play()` 被拒会停在黑屏 | 已复现：受控夹具在 hold 中把 `muted` 切为 `false` 并拒绝放行 `play()`；`playVideo()` 吞掉 `NotAllowedError`，video 保持 paused，`starting` 已回落 idle。真实页面确认已播放后开声音不会重调 `play()`，风险只在该窄窗口。 |
| P2 | hold 内 `src` 暂失，`starting` 残留 | 已复现：`canplay` 后进入 `starting`，重渲染为 `src=undefined` 仍显示 preparing。effect 在 `setStarting(false)` 前执行 `if (!video || !src) return`。 |

### 已排除的候选风险

- **缺片/解码洞补零直接制造通过质量门的假峰：未复现。**
  - 无关随机信号共享 `8–25s` 零洞：互相关全部返回 `null`。
  - 有真实 `2s` 延迟的信号共享 `8–22s` 零洞：全部稳定定位 `lagSec=2`，peak 为 `0.75–0.90`，sharpness 为 `13.9–26.7`。
  - 当前 `src/sync/xcorr.ts` 已为每个 lag 的真实交集重算 Pearson NCC，现有可构造边界没有显示零洞会造成误校准。`assemble()` 尚无 validity mask 仍是结构限制，但不得表述为已证实的 bug。

### 真实预览复核

在 `http://[::1]:5210/` 直播仍在线时已确认：

- 11 路均为 `readyState=4` 且正在播放。
- 没有完全匹配 profile 的 `005 / 009 / 010` 均为 `mode: off`，无 seek、无变速。
- 有 profile 的 `004 / 006 / 007 / 008 / 011 / 012 / 013` 为 `synced`，误差约 `0–0.1s`。
- 手动关闭同步后，所有路 status 回落 `off`，速率为 `1`；再开启后只恢复有实测 profile 的路。
