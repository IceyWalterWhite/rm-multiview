# 沙盘地图：从 FPV 画面反解机器人位置与血量

2026-08-04 · 分支 `worktree-sandbox-map`

## 目标

在 rm-multiview 上新增一张沙盘，实时显示各机器人的位置、朝向与血量。
数据不来自任何接口，而是从**已经在播的十路 FPV 画面**里用视觉手段反解出来 —— 零额外带宽。

依据是官方操作手客户端在每一路第一视角里都渲染了同一套 HUD：
右下小地图上的绿色圆盘就是「我」（外挂一个三角指示朝向），左下血条上写着「当前/上限」。

**十路各看各的自机**，所以每台机器人只由它自己那一路负责 ——
多目标跟踪里最难的数据关联问题被天然绕开了。

## 运行位置（方案 A / B）

算法核心写成与环境无关的纯函数：`(rgba, width, height) → {pose, hp}`，不碰 DOM 也不碰 fs。

- **方案 A（浏览器端）**：从 `<video>` drawImage 到 canvas，`getImageData` 喂进去。零带宽。
- **方案 B（服务端）**：一个进程拉流跑同一套函数，前端只订阅结构化 JSON。

两者共用同一份代码，切换只换喂帧的那一层。

**方案 A 有一个硬前提**：`useHlsPlayer.ts` 现在是
`if (video.canPlayType('application/vnd.apple.mpegurl'))` 就走原生 HLS。
原生路径下 `<video>` 直连 CDN，canvas 被标记为 tainted，`getImageData` 抛 `SecurityError`。
Chrome 150 的 `canPlayType` 返回 `'maybe'`，所以**桌面 Chrome 现网也在走原生路径**。
必须先把「强制 hls.js」的修复合进来（MSE 喂的帧走 `blob:` URL，同源，canvas 干净）。
iOS Safari 无解，只能降级为无沙盘。

## 模块划分

```
src/vision/      与业务无关的 CV 原语：HSV、掩码、连通域、距离变换
src/rmui/        官方 HUD 的版面常量（ROI、颜色阈值）—— DJI 改版先打到这里
src/matchstate/  开赛检测（独立模块，另一个实时服务共用）
src/sandbox/     位置 / 血量 / 阵亡提取 + 逐路时序聚合
```

`matchstate` 单独成模块是需求：另有一个网页实时服务依赖开赛检测，
两边共用同一份判定，避免各写一套判据后互相打架。

## 判据与实测数据

素材：2026 复活赛第 30 场录屏，8 路机器人 852×480 + 导播 1920×1080，全长 2570s。
**480p 比生产的 1080p 更苛刻**，下面的数字是下界。

### 开赛检测

| 信号 | 判据 | 实测 | 适用形态 |
|---|---|---|---|
| **音频** | FPV 路是否数字静音 | 等待卡与回合间歇 **-120 dBFS（采样恒为 0）**，回合中 p50 = -30 dBFS。三个回合边界 425–857 / 1289–1721 / 2033–2462，**无抖动** | 方案 A / B |
| **视觉** | 左下血条上的阵营色占比 | 与「文字是否存在」这一独立信号一致率 **95.97%** | 方案 A / B |

音频是更强的信号 —— 二值、无抖动，而不是阈值判断，方案 A / B 都优先用它，视觉兜底。

**浏览器端拿音频与「多路必须静音」不冲突**。静音（`muted` 属性）只是播放端的开关，
分片字节里照样带着 AAC 音轨。数据路完全绕开播放路径：

```
播放路（用户听到的）   hls.js → MSE → <video muted>      ← 侧视角永远 muted
数据路（采样用的）     fLoader tee 复制分片「字节」→ tsDemux 抽 AAC
                       → OfflineAudioContext.decodeAudioData → Float32Array
```

关键在 `OfflineAudioContext`：它是 Web Audio 的离线渲染器，解码结果只存在于内存数组里，
没有任何节点连接 `destination`（也不调用 `createMediaElementSource`）—— 解码一万段
音频，用户也听不到一个采样点。这条路在 timecode-sync 里已经实现并验证过
（`teeLoader.ts` / `tsDemux.ts` / `audioCalib.ts`），沙盘开赛检测直接复用。

代价是复杂度：要接 hls.js 的 `fLoader`、处理 TS 解复用与 ADTS 解码差异。Safari 原生 HLS
会绕过 hls.js，`fLoader` 不触发，字节路和 canvas 路都断 —— 那时两个信号都没有，
状态机保持原状，视觉兜底也无从谈起。

音频**只能用 FPV 路** —— 导播主视角全程有解说（p5 = -33 dBFS，从不静音），拿它判开赛必然恒真。

被数据否决的候选：
- **顶部记分板存在性**：等待卡在该区域有蓝色内容（误报），无人机路因画面内嵌 letterbox
  而记分板不在那个归一化位置（漏报）。
- **画面静止度**（设想等待卡是静帧）：比赛中 p50 = 6.43，非比赛 p50 = **8.32** —— 非比赛反而动得更多。
  等待卡本身是动画，回合间歇还有回放与场地实拍。

### 位置与朝向

自机标记 = 绿色圆盘（480p 下直径约 7px）+ 紧贴外侧的小三角。

同屏另有两类绿，靠窄色相区间排掉：能量机关是黄绿（色相 ≈ 42），蓝方图标是青（色相 ≥ 90）。
自机是偏青的春绿，色相 ≈ 79。

阈值 `H∈[68,86] S≥90 V≥90`，在 1340 个存活帧上对比过四组：

| 阈值 | 检出率 | 多候选（歧义） |
|---|---|---|
| **68-86 / 90 / 90** | **93.7%** | **0.1%** ← 采用 |
| 64-88 / 78 / 78 | 94.3% | 0.9% |
| 62-88 / 70 / 70 | 94.6% | 1.5% |
| 55-92 / 60 / 60 | 95.2% | 15.7% |

放宽多检出不到 1pp，歧义却涨十几倍。**漏检只让沙盘沿用上一次位置，误检会把机器人画到错误的格子上** ——
后者是观众看得见的错，前者不是。

两个实现要点：

- **圆心取距离场峰值的质心**，不取连通域质心。1080p 下圆盘中央会渲染机器人编号，
  深色数字在掩码上打出一个洞，最大距离会摊成一圈；取「所有接近峰值的像素的质心」天然处理这种并列。
  质心则会被外挂的三角拽偏。
- **箭头在整张掩码上找**，不限于圆盘那个连通域。实测箭头常只以对角相接，
  480p 下甚至完全断开成 2~8px 的独立小块。

### 血量

ROI 就是人工量的 `(215,923)-(318,949)`（1080p）。**不要外扩**：
往上 6px 会框进血条顶沿的白色高光，自适应阈值下它会连成一片把相邻数字粘住（14 帧里粘坏 6 帧）；
往右会收进血条右端的斜切装饰。

固定二值化阈值走不通：血条填满时底色是亮青/亮红，白字对比度低，字形碎成几根线；
掉空时底色发暗又会过粗。改用**白度通道** `V×(255−S)/255` + **相对该帧最大值的阈值**。

单一比例也不存在：0.45 让「300/300」后三位粘连，0.70 让「198/200」某位裂开。
最终做法是**多假设**：阶梯 `[0.6, 0.55, 0.65, 0.5, 0.7, 0.45]` 各切一遍，
每个候选跑完分类并用「一个斜杠 + 两边都是数字 + 当前值不超上限」校验，然后**投票**。
票数相同才比平均模板距离 —— 不能比置信度，那是「最佳 vs 次佳」的相对间隔，
跨切分方案没有可比性（实测就因此把 198 读成过 196）。

字形分类用**多样本近邻**，样本从真实画面按真值监督配对提取，细节见 `tools/sandbox/README.md`。

**留出集精度：24/25 = 96.0%**（27 帧中 2 帧无血条）。
唯一一次读错是 `146 → 145`，其置信度 0.01，是全集最低 —— 置信度确实抓住了它。
两帧无血条的画面**都返回 null，0 次凭空捏造数字**。

上限必须一起读：比赛中吃增益会升级，同一机器人一场里上限会变（实测 200→250→300→400），
按角色写死一定错。

### 阵亡

阵亡时整个赛事 UI 灰度化：小地图变灰、血条被「模块状态」面板整个顶掉、中央弹出复活倒计时。

判据是顶部记分板的阵营色占比：

| 状态 | 阵营色占比 | 亮像素占比 |
|---|---|---|
| 存活（16 帧，含 20/200 濒死） | 0.347 ~ 0.749 | 0.79 ~ 0.98 |
| **阵亡** | **0.000** | 0.770 |
| 等待卡 | 0.547 | 1.000 |
| 全黑 / 断流 | 0.000 | **0** |

两个必须写清的陷阱：

1. **这不是「HUD 是否存在」的判据** —— 等待卡时记分板同样有色。
   只有在「回合进行中」成立之后，低饱和才能解读为阵亡。
2. **只看饱和度会把黑屏当阵亡** —— 两者同样是 0。
   阵亡的特征是 UI 仍在渲染、只是被抽掉了颜色，所以还要求「亮像素占比 ≥ 0.3」。
   这条是被自己写的测试抓出来的。

按需求，阵亡时沙盘沿用该机器人**最后一次识别到的坐标**、血量记 **0**。

### 战略目标血量（基地 / 前哨站）

四个数字长在**所有十路共享的同一条顶部记分板**上，任意一路读出来即可，多路还能互相校验 ——
与机器人血量「每台只有自己那一路能看到」正好相反。每回合重置。

ROI 都比数字本身紧，因为左右紧挨着必须避开的装饰：红方基地左侧的黄色尖角、
蓝方基地右侧的斜杠、两侧「前哨站」的白色标签字。它们都是满高的，靠笔画高度过滤挡不住，
会凑成第五个字形段让整帧读数作废。裁准之后 400/400 个字段全部切分成功。

**当前状态：480p 下尚不可用于生产。** 训练集自测 343/400 = **85.8%**
（机器人血量在留出集上是 96.0%）。典型错误是 `1500→500`（丢掉细窄的首位）
和 `4245→4215`（末两位混淆）。

字形样本必须与机器人血量**分开**：这套 UI 的字号更矮（5~6 行 vs 7 行），
而字格归一化是「按高度缩放并保宽高比」，于是同一个 `1` 在血量里占 3 列（细长好认）、
在前哨站里占 7 列（几乎满宽，与 `0` 混）。复用血量模板会稳定地把 1500 读成 500。

下一步是**用 1080p 素材重建样本集**而不是在 480p 上继续调参 ——
同一块 ROI 在 1080p 下字形约 9×13px，与让机器人血量做到 96% 的尺寸相当。

### 空中机器人

无人机那两路的小地图在别处、也更小（FPV 内嵌在左侧子画面，右侧是飞手与云台手两路摄像头）：
`(975,595)-(1243,735)@1080p`。自机图标是四旋翼形状（480p 下糊成圆角矩形），同样带绿色朝向箭头。
算法本身不用改 —— 传 `kind: 'drone'` 即可，距离场峰值照样落在机身中心。

**两路渲染不对称**：蓝方是整个机身图标为绿色（面积中位 22px，91% 的帧可检出），
红方只有朝向箭头是绿的、机身是白/灰（面积中位 3px，仅 3%）。
480p 下红方基本不可用；1080p 那块 ROI 面积是 4.5 倍，那 3px 碎片会变成约 14px，值得开播后重测。

哨兵没有操作手视角，拿不到位置，沙盘上不显示。

### 线格式

位置未知时发 `(-1, -1)`，渲染层据此不画。**阵亡时仍然发最后一次识别到的坐标**（血量为 0）——
灰化的小地图读不出新位置，但观众需要知道它倒在哪里。只有从未识别到过（比如那位全场
关掉小地图的操作手）才发 `(-1,-1)`。

### 三态，不是两态

`alive` / `dead` / `unknown` 必须分开。单路漏检率有 2~7%（遮挡、伤害泛光），
**把「没看见」当「死了」会疯狂误报**。`unknown` 时保留最后已知值并让 UI 按陈旧度褪色。

## 已知边界

- **有操作手全场关闭小地图**（实测 B2 蓝方工程，54/54 采样点 0 命中）。这一路只有血量没有位置。
  HUD 是操作手可配置的，不能假设十路都有图。
- **血量很低时的红色伤害泛光**会把绿色标记的 S/V 一起压下去，极端情况色相被拉到 66 而落到区间外
  （夹具 `B3Infantry@1660`）。已记录为已知边界而非放宽阈值。
- **无人机那两路的红方标记在 480p 下基本读不到**（3%）。ROI 已支持（`kind: 'drone'`），
  蓝方 91% 正常，但红方要等 1080p 素材才能定论。
- **基地/前哨站血量在 480p 下 85.8%，尚不可用于生产**，需用 1080p 素材重建样本集。
- **哨兵没有操作手视角**，因此拿不到位置，沙盘上不显示。若将来要补它的血量，
  顶部记分板上有双方全体机器人的血量条 —— 那是十路共享的同一份全局信息。尚未实现。
