## 4. 关键不变量（改之前先读这一节）

**排布只有一个来源。** `src/stage/gridSolve.ts` 的 `solve(W, H, desiredH)` 在**渲染期现算**，
不存 state。于是首帧、切布局、改窗口、拖动中都不可能出现过期值。别把它的结果搬进 `useState`。

- 列宽永远铺满、格子恒守 16:9、行距 6px；
- `MIN_TILE_FRAC = 0.34` 来自参考稿的 `minTilePct` **props 默认值**。
  代码里那个 `?? 22` 是 props 缺失时的兜底，**不是默认值**——抄错它会让列数随高度横跳；
- `MAX_AREA_FRAC = 0.73`：下半区（分隔条 + 沙盘）保底，等价于沙盘不小于页面总高 25%。
  拖动横条的上界用的是同一个常量（拖过去再弹回来只会显得像卡了）。

**网格里排的是「看得见的那几路」，不是全部十路。** 排不进去的挂在 `.sg-offscreen`
继续解码——**解码与显示是两回事**。那个容器必须是 `1px + opacity:0`，
**不能用 `display:none`**，后者会让浏览器把解码一并停掉，沙盘就瞎了几路。

**顺序的唯一写入口是 `src/stage/viewOrder.ts`。** 「固定到上方」走 `swap`（等长交换，
不会把末尾的路挤出可见区），「拖动重排」走 `move`（手机桌面图标语义）。
`reconcile` 按 id 集合增删——HLS 签名过期会让 `useCatalog` 产出内容相同的新数组，
按数组身份重置的话，用户排好的次序会被反复清零。

**沙盘只在沙盘布局下渲染。** `SandboxMap` 自带 IntersectionObserver + 动态 import，
「切到沙盘布局才下 7.6 MiB」由组件自身保证，不依赖调用方记得做懒加载。

## 5. 会绊倒你的坑

按踩到的顺序，全部是实测得来的。

### 5.1 三维 → 屏幕：三个都会「看着像对的」的错误

**① 别用 `getWorldPosition()` 定位标记。** 它要求矩阵已更新，而拾取/跟随会在两帧之间被调用——
实测十台车会全部投影到同一点（世界原点）。机器人组的父节点就是 scene，
`grp.position` 本身即世界坐标，直接读它。

**② 把标签抬到「世界空间的某个高度」会横向漂。** 相机是斜视的，越靠画面边缘漂得越多：
抬 1.1 m，画面中间的前哨只漂 4 px，贴场边的基地漂了 20 px，血条就飘到基地外面。
那是正确的透视，但对「贴在建筑上的标签」是错的——观众读的是它落在哪个像素上。
做法是**把抬高拆成两个分量**：横向取底面中心、纵向取建筑顶（见 `ObjectiveBars`）。

**③ `groundAt()` 取的是该点最高的那个面。** 地标底下正好立着建筑，射线打到的是
建筑自己的顶盖（基地约 1.2 m），等于把 ② 的漂移又吃回来。`projectField` 的高度基准
是**主行驶面**常量，不问地形。

### 5.2 地标坐标：GLB 是唯一权威

场地模型在瘦身管线里被剥光了节点名，按名字找不到基地。量法（`window.__rmField` 拿根节点）：

> 遍历所有 mesh 求世界包围盒 → 换回场地系（`fx = wx, fy = −wz, h = wy − 主行驶面`）
> → 筛「占地 < 2.5 m 且顶高 > 0.9 m」的细高件（排掉地板与坡道）→ 按 1.5 m 网格聚类。

四座目标各聚出 15~16 个 mesh 的一簇，红蓝完全对称：

```
基地    (±11.55, 1.62)       顶高 1.38 m
前哨站  (±3.09, 5.56/−2.31)  顶高 1.78 m
```

⚠ **基地不在 ±12.745。** `fieldMap.ts` 横轴标定用的那对「队色灯条」在 ±12.745，
但灯条是从基地往场边辐射出去的一排，比基地本体还外约 1.2 m。
拿它当基地位置，血条会偏到场地边缘——这个错误犯过一次。

自洽性检验有两条：红蓝互为绕 `(0, FIELD_CENTER_Y)` 的 180° 对称点（已写成回归测试，
这条一破血条就钉在空地上，而那在截图上看着仍然「像对的」）；
以及与规则手册「图 4-5 战场模块定位尺寸图」的标注一致（基地 X=25593、前哨 X=17008/Y=3643，
分别差 4 cm 与 8 cm）。满血值 5000 / 1500 出自手册 5.5。

### 5.3 底栏：这一行里总有个吃掉全部富余的元素

「路标挤不下就缩成 👇」的判据**必须在写全的状态下量**（`flushSync` 写全 → 看是否溢出）。

别再想着「算还剩多少富余」：经典布局里是 `flex:1` 的发送条，沙盘布局里是
带 `margin-left:auto` 的尾部——两种情况下 `scrollWidth` 都恒等于 `clientWidth`，
富余永远算成 0，一旦收起就再也展不开。**这个坑用两种不同的判据各踩了一次。**

740 px 断点是 main 上就有的：再窄下去输入框会被压到 100 px 以内。原先靠
`flex-wrap` + `.composer--bar{flex-basis:100%}` 实现；`.controls` 拆成
`.controls__row` 之后那条规则失效（新行是 nowrap），现在由 `LiveStage`
在同一个断点把发送条挪出第一行。

### 5.4 切布局会卸载整棵子树

`--side-col-w` 写在 `.stage-row` 的 inline style 上，切到沙盘布局时那个节点整个被卸载，
切回来是**新节点**。设它的 effect 依赖数组必须含 `layout`，否则侧列退回 CSS 兜底宽度——
表现就是「切回经典布局后机位错位」。同一类问题在 `useEnlarged` 上不存在
（它在 `toggle` 里现读 `rowRef.current`，不缓存）。

### 5.5 沙盘相机

`OrbitControls` 的 dolly 是**按比例**缩 `|相机−target|`：越近每格滚轮走的绝对距离越小，
于是越放大越推不动；而旋转半径就是这个距离，同一时刻拖动也跟着失灵。
那不是到了边界，是渐近退化——永远到不了头却一路越来越黏，比明确的硬停更像卡住。
现在给了 `minDistance = 2` / `maxDistance = 1.5×装场距离`，并开了
`zoomToCursor` 与 `screenSpacePanning`。

`enableDamping = false` 与机器人位置的临界阻尼弹簧（`stepSpring`）是**两回事**，
别混。「操作手感不要有阻尼」指的是前者。

### 5.6 测试与验收本身的坑

- **同步 `evaluate` 块里派发事件后立刻读 DOM 会读到 React 批处理前的旧值。**
  曾据此得出「拖动完全没反应」的错误结论——那是自己制造的假阴性。加 `await requestAnimationFrame`。
- **合成 `pointerdown` 会打断 OrbitControls**（`setPointerCapture` 找不到该 pointerId 就抛异常，
  整个画布交互卡死）。测点击时只派发 `click` / `dblclick`。
- **量像素前先用实际 `getBoundingClientRect()` 定位。** `.ob__box` 带 `scale(k)` 变换，
  拿未变换的内部偏移去取点会采到盒子外面——曾据此编出一套「`backdrop-filter` 让
  alpha 压不下去」的假诊断。**数字与理论算不拢时，第一嫌疑人是测量本身。**
- `src/sandbox/drone.eval.test.ts` 在满载并行下会超时（60 s 上限，单独跑 15~18 s）。
  已观察到两次，与本轮改动无关。

## 6. 未定的选择（没人拍板过）

1. **沙盘 3D 视角**：计划写的是俯视 `setView('top')`（理由：网格右下区尺寸小，斜视看不清），
   实际保留的是带 0.28 弧度后仰的 `fitTop()`。这是单方面偏离计划、且未确认的一处。

   700 px 宽时它还能排出 2 列 122 px 的机位，能用但很挤。
3. **`drone.eval.test.ts` 要不要单独调高 timeout。**
